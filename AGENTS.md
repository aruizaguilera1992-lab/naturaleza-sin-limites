# AGENTS
- Editorial content is saved atomically with save_editorial_piece using admin validation and optimistic locking; public blog reads use blog_posts_public and merge with immutable local articles (local slugs win), and previews share the HTML-escaped blog renderer. Why: prevents draft leaks, overwritten edits, unsafe markup and existing SEO regressions without touching transactional flows.
- Public reads of outings go through the activity_events_public view (fixed column allowlist); the base table is admin/service_role only. Why: keeps private meeting points and notes off the public API.
- Compact surfaces (calendar cells, chips) must use `getActivityCatalogImage` (activityProfiles.ts), which reads the pre-CDN local snapshots (barrancosImagenLocal / cragsImagenLocal / ferratasImagenLocal) instead of `profile.image`. Why: the catalog files overwrite `imagenGrande` with CDN assets at module load, and the asset proxy serves HTML in the dev preview, so only local /images/ paths render reliably everywhere.
- Adventure recommendation questionnaires share `AdventureQuestionnaire`; discipline files provide only their questions, answers, and completion behavior. Why: keeps visual structure and accessibility consistent without duplicating the flow UI.
- Vértigo Sapiens keeps its lightweight pre-evaluation in browser storage and sends only through the existing online request form. Why: preserves the current backend contract and avoids turning orientation into a diagnosis or purchase flow.
- Automatic 30% deposits (create-activity-deposit) require a validated scheduled outing; custom dates go through submit-request without payment and get a manual admin payment link. Why: never charge before availability is confirmed.
- Deposit checkouts must call prepare_deposit_checkout (service_role RPC) before creating a Stripe session; it extends the seat hold once to cover a persisted expires_at used in the idempotency key. Why: no chargeable session may outlive seat availability, and retries must reuse identical params.
- App emails are sent through the Lovable connector gateway for Resend (`https://connector-gateway.lovable.dev/resend/...` with the managed key plus the connection key), never `api.resend.com` directly. Why: `RESEND_API_KEY` now holds a gateway connection key, so a direct provider call would fail auth.
- tsconfig.app.json maps `zod` types to the copy bundled with @lovable.dev/mcp-js. Why: two zod versions are installed and MCP tool schemas must type-check against the version mcp-js expects.
- Booking and payment emails/previews share bookingEmail.ts; readBookingEmailContext recognizes manual confirmation only for an admin-emitted booking signal or its exact accepted enlace_pago notification, never date or booking status alone; scheduled confirmation uses the actual seat outcome. Why: generic payments also set booking status and notification payloads contain rendered text, so provenance must not be inferred from those fields.
- Login and the root OAuth callback share authReturn.ts for validated internal destinations; new OAuth requests carry next in the public login callback URL even when sessionStorage succeeds; session redirects use getUser and router replacement, with role checks kept in admin. Why: preserves destinations across new tabs or lost storage without granting permissions or allowing external redirects.
- Manual (kind=manual) payment links may carry an explicit `purpose=booking_deposit_confirmation` validated in create-payment-link/handler.ts; its evidence lives in notification_log.payload.presentation under its own dedupe key, and receipts reuse it only when an accepted send matches payment, booking, recipient, amount and current date. Why: confirmation emails need explicit admin intent without changing payment kind, seats or eligibility.
- CRM commercial state lives in contact_submissions.pipeline_stage, separate from status (booking/payment state); email/phone normalization and the 'formulario' history event are DB triggers, entry functions only set source. Why: keeps sales tracking from altering reservation/payment flows and covers every insert path.
- Admin detail panels (contact CRM, follow-up, notes) initialize their editable state from the record prop and rely on a per-record React key to remount; they must never re-sync that state from the prop object. Why: any list refresh (loadData) hands the panel a new object identity and would silently discard edits the admin has not saved yet.
- The admin contact detail (contact/ContactDetail.tsx) has a persistent header plus four forceMount tabs with exclusive roles (Ficha, Seguimiento, Reservas y pagos, Notas); proposals open in a dialog whose message state lives in ContactDetail, deletion lives in the header admin menu, and related bookings are read-only crmMatching results (email AND phone = related; one alone = possible). Why: switching tabs or closing the dialog must not drop unsaved edits, and ambiguous matches must never merge records.
- Newsletter signup is double opt-in through the newsletter edge function (subscribe/confirm/unsubscribe by token); consent_records is append-only evidence, and only status=confirmado subscribers may ever receive marketing. Why: commercial consent must be explicit, separate from contact requests, and provable.
- Newsletter campaigns use service-only state-transition RPCs, immutable audience snapshots, campaign/notification leases and per-recipient provider keys; the worker rechecks the same consent before sending and stops uncertain retries before the provider idempotency window expires. Why: protects opt-outs and prevents concurrent or late duplicate marketing without changing transactional notifications.
- Newsletter email preview and server delivery share the escaped newsletterContent renderer; newsletter editors initialize per-record state and remain mounted across tabs. Why: preview matches delivery and navigation preserves unsaved edits independently from blog publication.
- /barranquismo shows the curated commercial selection in canyonCatalog.ts (commercial level separate from technical grade); only items mapped to an identical existing barrancos product get ficha/reserva and price, others are no-charge consults with a photo-pending panel. Why: the technical barrancos dataset and its CDN photos are not geographically/licence-verified commercial offers.
- Barranquismo and Vías ferratas are sold as three level offers (levelOffers.ts, LevelOffersSection) like Espeleología; individual route datasets stay unpublished in catalog listings and the «Desde» price is derived from existing product prices. Why: no verified photos per route and the user chose level-based presentation.
- Private activity sheets (activity_sheets) are admin-only; customers read one only via get_activity_sheet(token), which requires status=enviada and not expired; emails go through send-activity-sheet (HTML in _shared/activitySheetEmail.ts) using the shared tracked notification sender; customers accept via accept_activity_sheet(token), which idempotently creates a pending booking without charging — the 30% deposit link is sent manually by admin. Why: links stay unguessable and revocable without exposing the table publicly.
- Admin «Salidas» unifies open groups (activity_events, public calendar + deposit) and private groups (activity_sheets); the original catalog stays in code and catalog_entries stores only admin overrides plus own photos in the private catalog-photos bucket, readable only by admins; customers get a short-lived signed URL for their sheet photo via the activity-sheet-photo function (validates the sheet token). Why: public site keeps level offers while the admin can edit every route without seeding data, and the workspace blocks public buckets.
- Deleting an open-group outing goes only through admin_delete_activity_event, which refuses while a non-liberada activity_event_bookings row exists; private sheets go through admin_delete_activity_sheet with the same accepted-with-booking guard. Why: an active reservation or payment must never lose its evidence, and deletion stays a single-record admin action.

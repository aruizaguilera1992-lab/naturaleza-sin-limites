# AGENTS
- Public reads of outings go through the activity_events_public view (fixed column allowlist); the base table is admin/service_role only. Why: keeps private meeting points and notes off the public API.
- Compact surfaces (calendar cells, chips) must use `getActivityCatalogImage` (activityProfiles.ts), which reads the pre-CDN local snapshots (barrancosImagenLocal / cragsImagenLocal / ferratasImagenLocal) instead of `profile.image`. Why: the catalog files overwrite `imagenGrande` with CDN assets at module load, and the asset proxy serves HTML in the dev preview, so only local /images/ paths render reliably everywhere.
- Adventure recommendation questionnaires share `AdventureQuestionnaire`; discipline files provide only their questions, answers, and completion behavior. Why: keeps visual structure and accessibility consistent without duplicating the flow UI.
- Vértigo Sapiens keeps its lightweight pre-evaluation in browser storage and sends only through the existing online request form. Why: preserves the current backend contract and avoids turning orientation into a diagnosis or purchase flow.
- Automatic 30% deposits (create-activity-deposit) require a validated scheduled outing; custom dates go through submit-request without payment and get a manual admin payment link. Why: never charge before availability is confirmed.
- Deposit checkouts must call prepare_deposit_checkout (service_role RPC) before creating a Stripe session; it extends the seat hold once to cover a persisted expires_at used in the idempotency key. Why: no chargeable session may outlive seat availability, and retries must reuse identical params.
- App emails are sent through the Lovable connector gateway for Resend (`https://connector-gateway.lovable.dev/resend/...` with the managed key plus the connection key), never `api.resend.com` directly. Why: `RESEND_API_KEY` now holds a gateway connection key, so a direct provider call would fail auth.
- tsconfig.app.json maps `zod` types to the copy bundled with @lovable.dev/mcp-js. Why: two zod versions are installed and MCP tool schemas must type-check against the version mcp-js expects.
- Booking and payment emails/previews share bookingEmail.ts; readBookingEmailContext recognizes manual confirmation only for an admin-emitted booking signal or its exact accepted enlace_pago notification, never date or booking status alone; scheduled confirmation uses the actual seat outcome. Why: generic payments also set booking status and notification payloads contain rendered text, so provenance must not be inferred from those fields.
- Login and the root OAuth callback share authReturn.ts for validated internal destinations and storage failure handling; session redirects use getUser and router replacement, with role checks kept in admin. Why: preserves consent flows and prevents external redirects or access loops without granting permissions.
- Manual (kind=manual) payment links may carry an explicit `purpose=booking_deposit_confirmation` validated in create-payment-link/handler.ts; its evidence lives in notification_log.payload.presentation under its own dedupe key, and receipts reuse it only when an accepted send matches payment, booking, recipient, amount and current date. Why: confirmation emails need explicit admin intent without changing payment kind, seats or eligibility.
